# Codex 作業指示: ゴールからの逆算と、タスクの自動推薦

作成: 2026-10-22。この 1 ファイルだけ読めば着手できるように書いている。不明点は推測で進めず、§9「判断が必要な点」に記録してから、安全な側で進めること。

## 1. ユーザーの要望

- **目標（ゴール）を設定し、その期日から逆算してタスクに分解したい。**
- **ChatGPT の対話履歴、Gmail、マインドマップから分解したタスクなどを、うまい仕組みで自動的に推薦してほしい。**

`docs/VISION.md` の柱 1「ゴールでつながる ToDo」と柱 4「AI が ToDo を集めてくる（承認つき）」を、1 つの流れとしてつなぐ作業にあたる。

## 2. 目指す体験

```
ゴール（期日・成功の定義）
   └─ 逆算した計画: マイルストーン → 期日付きのタスク        … 承認してから保存
ChatGPT の履歴 / Gmail / マインドマップ / ゴールの計画 / MCP
   └─ すべて同じ「候補」として受信箱に集まる
        └─ 関係するゴールを推定し、点数と理由を付けて並べる
             └─ 人が承認したものだけがタスクになる（自動では登録しない）
今日の画面 / 秘書
   └─ ゴールの期日・放置日数・空き時間を考えて「次の一手」を推薦する
```

**推薦には必ず理由を付ける**（例:「ゴール『TOEIC 800点』に関係」「期日まで 12 日、計画より 2 日遅れ」「このゴールは 5 日間手つかず」）。点数だけの推薦や、理由の分からない並び替えはしない。

## 3. 現状（2026-10-22 時点で確認した事実）

コアの部品はほとんどそろっているが、**互いにつながっておらず、Web 版にも出ていない**。

| 機能 | 場所 | 状態 |
|---|---|---|

| ゴールの AI 分解（子ゴール ＋ タスク） | `goals.propose_goal_breakdown` → 確認 → `apply_goal_breakdown` | Web API あり。ただし**1 段だけ**で、期日は `due_hint`（「来週」などの文字列）だけ。**期日からの逆算・マイルストーンの期日・間に合うかの確認はない** |
| ゴール表の列 | `goals`: `why`, `success_criteria`, `target_date`, `status` | 逆算に必要な列はすでにある |
| 未分類タスクのゴールへの割り当て提案 | `goals.propose_task_goal_assignments` | AI のみ。候補（未承認）には使われていない |

| メール・会話からの候補抽出 | `core/task_extraction.py`（`extract_task_candidates`） | 出典ごとにまとめて 1 回の AI 呼び出し。信頼しない入力として扱う |

## 4. 設計方針

### 4.1 すべての出どころを「候補」に一本化する
- ChatGPT・Gmail・マインドマップ・ゴールの逆算計画・MCP・（将来）カレンダーの準備タスクを、すべて `task_candidates` に入れる。承認の操作は 1 か所（受信箱）にまとめる。
- マインドマップから手動で「タスクにする」操作（既存）は残す。それに加えて「候補として受信箱に送る」経路を足す。
- ゴールの逆算計画は、確認画面でまとめて承認する既存の流れ（`apply_goal_breakdown`）を基本とする。あとで承認したい分だけを候補に回せるようにしてもよい。

### 4.2 候補に足す情報（追加のマイグレーションのみ）
`task_candidates` に列を追加する（SQLite と PostgreSQL の両方。既存の列は変えない）。

| 列 | 内容 |
|---|---|
| `goal_id` | 推定したゴール（NULL 可。承認時にユーザーが変更できる） |
| `goal_match` | ゴール推定の確からしさ（0〜1）と方法（`ai` / `rule`） |
| `score` | 推薦の点数（並び順に使う） |
| `reasons` | 理由の配列（JSON 文字列）。画面にそのまま出す短い日本語 |
| `estimate_minutes` | 見積もり（任意） |
| `scored_at` | 点数を付けた日時（再計算の判定に使う） |

`source` には `mindmap` と `goal_plan` を追加する。値は DB の制約ではなく `candidates.ALLOWED_SOURCES`（`gmail`, `slack`, `notion`, `chat`, `calendar`, `other`）で限定しているので、そこに足す。MCP から受け付ける値と、画面での出どころの表示も合わせて確認する。

### 4.3 推薦の点数は「決定的で説明できる」計算にする
- AI は、**ゴールの推定と見積もりの補助**にだけ使う。点数そのものは、Python の純粋な関数（`core/recommend.py` などの新規モジュール）で計算する。こうすれば pytest で固定でき、AI がなくても動く。
- 要素の例（重みは定数にまとめ、テストで並び順を固定する）:
  - **ゴールとの関係**: 推定の確からしさ × ゴールの重要度（今は有効なゴールかどうかだけ。ゴールに優先度の列を足すかは §9）
  - **ゴールの緊急度**: 期日までの残り日数と、計画からの遅れ
  - **放置**: `stale_goals` の放置日数が長いゴールの候補を少し上げる
  - **タスク自身の期限**: 候補の `due_date`
  - **抽出の自信度**: `confidence`
  - **出どころの実績**: 出どころごとの承認率（§4.5）
  - **減点**: 既存タスクや却下済みの候補とよく似ているもの（`task_ai._bigrams` のような軽い類似度で判定する）
- 各要素から、理由の文を 0〜2 個作って `reasons` に入れる。

### 4.4 ゴールからの逆算
- 入力: ゴールの `title`・`why`・`success_criteria`・`target_date`・既存の配下タスクと完了状況・（任意で）1 日に使える時間。
- 出力（保存前の提案。既存の `GoalBreakdown` を拡張するか、新しいデータクラスにする）:
  - **マイルストーン**（子ゴール）: それぞれ `target_date` を持つ。最後のマイルストーンはゴールの期日以前にする
  - **タスク**: それぞれ `due_date`（実際の日付）・`estimate_minutes`・どのマイルストーンに属するか
  - **実現性の確認**: 見積もりの合計と、期日までに使える時間を比べる。足りなければ「間に合わない可能性」と、削る・延ばす案を返す
- 期日の割り当ては Python で行う。AI が返すのは順番と見積もりだけにする（日付の計算を AI に任せない）。
- AI が使えないときは、ルールで代替する: 残り期間を等分したマイルストーンの枠と、「最初の一歩」タスク 1 件を提案し、その旨を表示する。
- 期日のないゴールは、逆算せず従来の分解を使う。期日の入力を促す。
- 承認してから保存する。既存の `apply_goal_breakdown` と同じく、選んだ項目だけを保存する。

### 4.5 承認・却下から学ぶ（ローカルで、単純に）
- 承認・却下のたびに、出どころ別・ゴール別の承認率を集計する（新しい表、または `task_candidates` の集計で済むならそれでよい）。
- 点数の「出どころの実績」に使う。件数が少ないうちは中立の値にする（例: 事前分布を置いた平均）。
- 外部への送信や、機械学習モデルの学習はしない。

### 4.6 取り込みの自動化
- **ChatGPT**: ChatGPT の会話履歴を外から読む公式 API はない。経路は次の 3 つにする。
  1. エクスポート（zip/JSON）のアップロード（既存の `parse_export` を使う）
  2. 会話の貼り付け（既存の `parse_pasted_text`）
  3. ChatGPT 側から MCP の `propose_tasks` で候補を送る（既存）
  Web では 1 と 2 の API・画面を追加する。アップロードのサイズ上限を設け、ファイルはサーバーに保存せず、その場で解析する。
- **Gmail**: 現在はキーチェーンに認証情報を保存するので、**ローカル版のみ**で動く。ローカル版では「最近のメールを取り込む」操作と、任意の定期実行（既存の `calendar_sync` のような仕組み）を用意する。処理済みのメールは `mark_processed` で二重取り込みを防ぐ。**公開 Web 版での Gmail 連携は、このタスクでは実装しない**（理由は §9）。
- **マインドマップ**: ひらめきのセッションで「行動計画を候補にする」操作を足す。ノードの `id` を `source_ref` にして、二重登録を防ぐ。
- **AI に送る前の同意**: メールや会話の本文を AI に送る操作の前に、何を送るかを示して同意を取る（初回のみでよい。設定で取り消せる）。

### 4.7 推薦の出し方
- **受信箱**: 候補を `score` の高い順に並べ、理由・推定したゴール・出どころを表示する。ゴールはその場で変更できる。承認・却下・あとで、を 1 タップでできるようにする。
- **今日**: 「次の一手」の選び方に、ゴールの緊急度・遅れ・放置を加える。既存の `secretary.next_action` の外から見える結果（期限切れが最優先など）は保ったまま、同じ順位の中での並べ方に使う。
- **ゴール画面**: ゴールごとに「計画どおり / 遅れ気味 / 間に合わない可能性」と、次にやる 1 件を表示する。
- 一度に推薦する数には上限を設ける（例: 受信箱の上位を強調するのは 5 件まで）。量で圧倒しない。
- UI は `docs/redesign/CODEX_GAME_UI_BRIEF.md` で決めるデザインに合わせる。**あちらのフェーズ 1（`App.tsx` の分割）が終わるまで、このタスクの UI 変更（フェーズ D）は始めない**。同じファイルを同時に書き換えて衝突するのを避けるため。API とコアの作業は先に進めてよい。

## 5. 作業フェーズ（PR を分ける）

各フェーズを独立した PR にし、`main` から `codex/goal-reco-<フェーズ>` のブランチを切る。

### フェーズ A: データと点数計算（UI なし）
- `task_candidates` への列の追加（SQLite のマイグレーション ＋ PostgreSQL のスキーマ。既存 DB の移行テストを付ける）。
- `core/recommend.py`（仮の名前）: 点数と理由の計算、ゴールの推定（AI ＋ ルールでの代替）、類似度による減点、承認率の集計。
- 候補の作成時と、ゴールの変更時に点数を再計算する。
- pytest: 並び順の固定、理由の文、AI がないときの動作、2 ユーザーの分離。

### フェーズ B: ゴールからの逆算
- コア: 逆算の提案（AI ＋ ルールでの代替）、Python での日付の割り当て、実現性の確認、選んだ項目の保存。
- API: 既存の `/api/goals/{id}/breakdown` を拡張するか、新しいエンドポイントにする。**既存のレスポンスのフィールドは消さない**。
- pytest: 期日が近い・遠い・過ぎている・期日なし、見積もりが足りない場合、うるう年や月末をまたぐ日付。

### フェーズ C: 取り込み経路
- Web API: ChatGPT のアップロード・貼り付け → 候補、マインドマップ → 候補。
- ローカル版: Gmail の取り込みで新しい点数付けを通す（任意で定期実行）。
- AI に送る前の同意の保存と確認。
- pytest: 二重取り込みの防止、上限サイズ、信頼しない入力（プロンプトインジェクションを含む本文）が候補の文字列として安全に扱われること。

### フェーズ D: 推薦の UI
- 受信箱の並び替えと理由の表示、ゴールの変更、ゴール画面の進捗状態、今日の「次の一手」の改良、逆算の確認画面。
- ゲーム UI の作業と重ならないよう、§4.7 の順序を守る。

## 6. 守ること

1. `AGENTS.md` に従う。**`symnote.db`・`data/`・`backups/`・`.env` を開かない・変更しない・コミットしない。** 確認には一時 DB（`DB_PATH` を一時ファイルに）を使う。
2. マイグレーションは追加のみ。`SCHEMA_VERSION` を上げ、古い DB から起動しても壊れないことをテストする。PostgreSQL のスキーマにも同じ変更を入れる。
3. **人が承認するまで、外部由来の候補をタスクにしない**（VISION の柱 4）。自動承認の設定は作らない。
4. **AI・API キー・ネットワークがなくても動く**。点数計算と並び替えはルールだけで成り立つようにし、AI を使う部分だけを無効にして理由を表示する。
5. メール・会話・マインドマップの本文は信頼しない入力として扱う（既存の `task_extraction` の方針を守る）。画面ではテキストとしてだけ描画し、`dangerouslySetInnerHTML` を使わない。
6. MCP（`symnote.mcp_server`）のツールの入出力と、カレンダー同期の挙動を変えない。`get_next_actions` の並びを改良する場合は、互換性を保つ形で行い、テストで確認する。
7. Gmail の認証情報・OAuth の値・`~/.secrets/` を読まない・出力しない。テストでは `gmail_import` の外部呼び出しをすべて差し替える（既存の `_guard_credentials` を尊重する）。
8. AI の呼び出し回数と送る文字数に上限を設ける（既存の `usage_limit.py` と `task_extraction` のまとめ方に合わせる）。
9. コード内コメントとドキュメントは日本語。コメントは「なぜそうしないか」だけを書く。コミットメッセージには「なぜ」を書く。

## 7. 検証方法

```sh
.venv/bin/python -m pytest -q
cd web && npm run build && npm run test:device
```

- PostgreSQL の統合テストは `SYMNOTE_TEST_POSTGRES_DSN` があるときだけ動く。使えない環境では、SQLite での確認とスキップしたことを PR に書く。
- 画面の確認は、一時 DB で `symnote.web_server` と `npm run dev` を起動して行う（起動方法は `docs/redesign/CODEX_GAME_UI_BRIEF.md` の §7 と同じ）。確認用のゴール・候補は API 経由で一時 DB に作る。
- PR には、推薦の並び順の例（入力の候補と、出てきた順位・理由）を載せる。

## 8. 完了の定義

- 期日付きのゴールから、マイルストーンと期日付きのタスクが提案され、選んだものだけが保存される。間に合わない場合は警告と代替案が出る。
- ChatGPT（アップロード・貼り付け）・マインドマップ・（ローカル版の）Gmail・MCP から来た候補が受信箱に集まり、推定したゴール・点数・理由付きで並ぶ。
- 承認・却下の結果が、以後の並び順に反映される。
- 今日の「次の一手」が、ゴールの期日・遅れ・放置を考えた理由付きで出る。
- AI がない状態でも、上の流れがルールベースで動く。
- pytest・`npm run build`・`npm run test:device` がすべて通る。2 ユーザーの分離テストも通る。

## 9. 判断が必要な点（ユーザーに確認すること）

フェーズ A の PR を出すときに、少なくとも次を確認する。

- **公開 Web 版での Gmail 連携をどうするか。** Gmail の読み取り権限（`gmail.readonly`）は Google の「制限付きスコープ」で、公開アプリで使うには Google の審査と、外部のセキュリティ評価が必要になる。案は次の 3 つ。
  - ローカル版だけで提供する（今回の前提）
  - メールの転送・貼り付けで取り込む
  - 審査を受けて正式に対応する
- ゴールに「優先度」の列を足すか（今はゴールの重みを付けられない）。
- 1 日に使える時間を、設定値として持つか、Google カレンダーの空き時間から求めるか。
- 推薦の上限数と、点数の重みの初期値。
