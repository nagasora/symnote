# Codex 作業指示: Web UI の全面改良（「ゲーム感覚でタスクをこなす」体験）

> **2026-10-22 更新: この指示書は `docs/redesign/game/CODEX_GAME_REDESIGN.md` に置きかえられました。Codex には新しいほうを渡してください。** 世界観・配色・絵柄は新しい指示書で決定済みです。

作成: 2026-10-22。この 1 ファイルだけ読めば着手できるように書いている。不明点は推測で進めず、「判断が必要な点」（§8）に記録してから、安全な側で進めること。

## 1. ユーザーの要望（原文の意図）

- デザインを大きく改良したい。**もっと使いやすい構造**にしたい。
- AI が作ったタスクを **「ゲーム感覚でこなす」雰囲気** にしたい。
- **もっと見やすく、使いやすいアプリ** にしたい。
- まずアプリ全体の雰囲気を改良する。**色・雰囲気・絵柄（イラストやキャラクター）などのデザインが必要かどうかも含めて、Codex が考えて決めてよい。**

優先順位は **見やすさ・使いやすさ ＞ ゲーム感**。ゲーム要素は、タスクをこなす気持ちを後押しする量にとどめる。`docs/VISION.md` の調査では Habitica について「見た目が雑多で、タスク管理としては弱い」とまとめている。この失敗を繰り返さないこと。

## 2. 対象範囲

| 対象 | 扱い |
|---|---|
| Web 版 React UI（`web/src/`） | **主対象**。構造・見た目・操作を改良する |
| Web API（`src/symnote/api/`） | ゲーム要素の表示に必要な**読み取り・操作 API の追加**だけ行う |
| `src/symnote/core/` | 既存のロジックを使う。変更は最小にし、pytest を付ける |
| iOS 画面（`web/src/NativeCapture.tsx`） | 今回は対象外。デザイントークンを共有できる形にしておくだけ |
| Streamlit 版（`src/symnote/app.py`, `views/`） | 変更しない |
| MCP（`symnote.mcp_server`）・カレンダー同期 | 挙動を変えない |

## 3. 現状（2026-10-22 時点で確認した事実）

### 3.1 画面と構造
- `web/src/App.tsx`（約 2,300 行）に、全画面・状態・API 呼び出しが **1 つのコンポーネント** として入っている。改良の前に分割が必要。
- 画面は 5 つ（`ScreenId`）: **今日** / **受信箱**（あとで）/ **すべて**（一覧・ゴール・カレンダーの切り替え）/ **ひらめき** / **設定**。
- PC はサイドバー、スマホは下部タブバー。クイック入力（⌘K / ＋）と、右側の詳細パネルがある。
- ゴール画面は `web/src/GoalsView.tsx`。
- スタイルは `web/src/styles/tokens.css`（方向性②「やわらかい紙のノート」: 生成り色の紙、明朝の見出し、紺のアクセント、紙のざらつき）と `web/src/styles/app.css`（約 470 行）。ライト・ダークの両方に対応している。
- 前回の刷新計画とモックは `docs/redesign/PLAN.md` と `docs/redesign/mockups/` にある。情報設計（4 画面 ＋ 設定）や守ることは参考になる。ただし見た目の方向性は、今回 Codex が見直してよい。

### 3.2 ゲーム要素の資産（使われていないものが多い）
- `src/symnote/core/quest.py`: タスク完了時の XP・ゴールド・レベル・称号・連続日数・実績・ご褒美の交換。`db.py` の完了処理から `award_for_completion_in_transaction` が呼ばれ、**Web 版でも報酬は記録されている**（PostgreSQL にも `quest_log` テーブルがある）。
- しかし **Web API はこれを公開していない**。`POST /api/tasks/{id}/complete` が返すのは `task` と `next_task` だけで、獲得した XP・レベルアップ・実績を UI が受け取れない。
- `src/symnote/core/focus.py`: フォーカスセッション（集中タイマー・集中ボーナス）。これも Web API に出ていない。
- `src/symnote/core/secretary.py`: 秘書キャラクター（`avatar_svg`、ひとこと反応の `reaction_for`、`next_action`）。Web には出ていない。
- `docs/VISION.md` の「クエスト化」方針: 完了時の「QUEST CLEAR!」演出、経験値・ゴールド・レベル・称号・実績、自分で決めたご褒美との交換。**期限切れでも減点しない（責めない設計）**。

## 4. Codex に任せる判断（デザインの方向性）

次の項目は、Codex が調べて決めてよい。決めた内容と理由は `docs/redesign/GAME_UI_DIRECTION.md` に残すこと。

1. **世界観と雰囲気**: 現行の「紙のノート」を活かしてゲーム要素を足すのか、別の世界観（例: 冒険の手帳、クエストボード、ドット絵風など）に変えるのか。比較案を 2〜3 個出し、1 つを選んで理由を書く。
2. **配色・タイポグラフィ**: 新しいトークンを決める。ライト・ダークの両方で **WCAG AA のコントラスト** を満たすこと（本文 4.5:1、大きい文字・UI 部品 3:1）。
3. **絵柄が必要か**: キャラクター（秘書）、アイコン、バッジ、背景イラストが必要かを判断する。必要なら次のどちらかで作る。
   - SVG または CSS をリポジトリ内で自作する（推奨。ライセンスの問題がない）
   - 外部素材は、商用利用・改変が可能なライセンスのものだけ使う。出典とライセンスを `docs/redesign/ASSETS.md` に記録する
   - 生成画像を使う場合も、出典の記録と、ライト・ダーク両方での見え方の確認を行う
4. **ゲーム要素の量**: 何を常に見せ、何を完了の瞬間だけ見せるか。目安は「常に見せるのは小さな HUD（レベル・XP バー・今日の達成数）だけ。演出は完了の瞬間だけ」。

### 判断の基準
- **3 秒で今日やることが分かり、1 タップで完了できる**（PLAN.md のゴールを引き継ぐ）。
- 一番目立つのは常に「次にやるタスク」。ゲームの装飾がタスク名より目立ってはいけない。
- 責めない: 期限切れは警告色で数えて並べるのではなく、「再挑戦」できる見せ方にする。減点・失敗演出は作らない。
- AI が作ったタスクと分かる印（出どころ）を残す。AI の候補は承認するまでタスクにならない（既存の受信箱フローを維持する）。
- `prefers-reduced-motion` のときは演出を最小にする。音は、入れる場合も既定でオフにする。

## 5. 作業フェーズ（PR を分ける）

各フェーズは**独立した PR** にする。前のフェーズがマージされてから次に進む。ブランチ名は `codex/game-ui-<フェーズ>` とし、`main` から切る。

### フェーズ 0: 方向性の決定（コードは変えない）
- `docs/redesign/GAME_UI_DIRECTION.md` を作る。内容は、比較案・採用案と理由・トークン案（色・文字・角丸・影・動き）・画面ごとの構成案・ゲーム要素の一覧（常時表示 / 完了時 / 専用画面）。
- 必要なら、静的なモック（HTML、または `docs/redesign/mockups/` に置くスクリーンショット）を作る。
- **ここで一度止まり、ユーザーの確認を受ける。** 確認が取れるまでフェーズ 2 以降に進まない（フェーズ 1 は見た目を変えないので並行してよい）。

### フェーズ 1: 構造の分割（見た目と挙動は変えない）
- `App.tsx` を画面別・部品別に分ける。目安の構成:
  - `web/src/screens/`（Today, Inbox, All, Ideas, Settings）
  - `web/src/components/`（TaskCard, DetailPanel, QuickCapture, Sidebar, TabBar など）
  - `web/src/hooks/` または `state/`（データ取得・更新）
- API 呼び出しは `web/src/api.ts` に集約する。
- **画面の表示と操作が分割前と同じ**であることを確認する（§7 のスクリーンショット比較）。

### フェーズ 2: 新しいデザインシステムの適用
- `tokens.css` を新しいトークンに置き換え、`app.css` を部品ごとに整理する。
- ナビゲーション・ページ見出し・カード・ボタン・空状態・読み込み中・エラー表示を統一する。
- 使いやすさの改善: 情報の優先順位、余白、文字サイズ、タップ領域（最小 44×44px）、キーボード操作、フォーカス表示。

### フェーズ 3: ゲームの層（API ＋ UI）
- API の追加（`src/symnote/api/` と `schemas.py`。各エンドポイントに pytest を付ける）:
  - プレイヤー情報（レベル・称号・XP・次のレベルまで・ゴールド・連続日数・今日の完了数）
  - 完了の応答に、その完了で得た報酬（XP・ゴールド・ボーナス・レベルアップ・新しい実績）を**追加フィールドとして**含める。既存のフィールドは変えない
  - 実績一覧、ご褒美の一覧・登録・交換（`InsufficientGoldError` は 400 系の分かりやすいエラーにする）
  - 必要ならフォーカスセッションの開始・終了
- **ユーザーごとの分離を守る**: Web は PostgreSQL のユーザー別スキーマ（`user_scope`）で動く。quest・focus の関数がリクエストのユーザーの範囲だけを読み書きすることを、2 ユーザーのテストで確認する。
- UI:
  - 小さな HUD（レベル・XP バー・今日の達成数・連続日数）
  - 今日の画面を「今日のクエスト」として見せる（AI が提案した順番・見積もり・ゴールとのつながり）
  - 完了時の「QUEST CLEAR!」演出（XP の加算、レベルアップ、実績の解除）。演出中も次の操作を妨げない
  - 実績とご褒美を見る場所（設定の中か、新しい画面かはフェーズ 0 で決める）

### フェーズ 4: 仕上げ
- 残りの画面（受信箱・すべて・ひらめき・設定）を新しいデザインに合わせる。
- 1440px / 1024px / 390px、ライト / ダーク、`prefers-reduced-motion` の全組み合わせを確認する。
- `docs/02_spec_ui.md` を新しい構成に合わせて更新する。

## 6. 守ること

1. `AGENTS.md` に従う。**`symnote.db`・`data/`・`backups/`・`.env` を開かない・変更しない・コミットしない。** 動作確認には必ず一時 DB を使う（§7）。
2. マイグレーションは追加のみ。既存の SQLite 利用者の DB と PostgreSQL の両方で動くようにする。
3. **AI や API キー、ネットワークがなくても** 今日・受信箱・すべて・クイック入力・設定が動く。AI を使う操作だけを無効にし、理由を表示する。
4. 外部由来の文字列（タスク名・メモ・候補の抜粋）は常にテキストとして描画する。`dangerouslySetInnerHTML` を使わない（現在 0 件。増やさない）。SVG を差し込む場合は、リポジトリ内の静的なファイルか、React の要素として書く。
5. 既存 API のレスポンスからフィールドを削除・改名しない（iOS や MCP からの利用を壊さない）。
6. 新しい npm 依存は最小にする。追加するなら、理由・バージョン固定・`npm audit` の結果を PR に書く。
7. コード内コメントとドキュメントは日本語。コメントは「なぜそうしないか」だけを書く。コミットメッセージには「なぜ」を書く。
8. 秘密情報（`~/.secrets/`、API キー、OAuth の値）を読まない・出力しない。

## 7. 検証方法

### 自動テスト（すべての PR で実行する）
```sh
.venv/bin/python -m pytest -q
cd web && npm run build && npm run test:device
```
- フロントエンドに単体テストの仕組み（Vitest など）を入れる場合は、フェーズ 1 の PR で入れ、HUD の計算や完了演出の状態遷移をテストする。

### 画面での確認
一時 DB で API とフロントエンドを起動する。

```sh
export DB_PATH="$(mktemp -d)/symnote-ui.db"
.venv/bin/python -m symnote.web_server --host 127.0.0.1 --port 8000
# 別のターミナルで
cd web && npm run dev   # http://localhost:5173 （/api は 8000 へ転送される）
```
- ローカル認証の挙動は `src/symnote/api/auth.py` の `auth_mode()` と `is_loopback_request()` を確認すること。ログインできない場合は、E2E 用ログイン（`SYMNOTE_E2E=1` と `/api/auth/e2e-login`）をローカルでのみ使う。
- 確認用のタスク・ゴール・メモは、API 経由で一時 DB に作る（ユーザーの実データを使わない）。
- 各フェーズで、主要画面のスクリーンショットを 1440px / 390px × ライト / ダークで撮り、`outputs/ui-screenshots/<フェーズ>/` に保存する。`outputs/` はコミットしない（現在 `.gitignore` に含まれていないので、フェーズ 1 の PR で `outputs/` を追加する）。PR には、変更前と変更後の比較を数枚載せる。

## 8. 判断が必要な点（ユーザーに確認すること）

フェーズ 0 の報告で、少なくとも次を確認する。

- 採用する世界観と配色（比較案のどれにするか）
- 秘書キャラクターを Web の画面に出すか。出す場合の絵柄
- 実績・ご褒美を独立した画面にするか、設定や今日の画面に含めるか
- 音（効果音）を入れるか

## 9. 完了の定義

- フェーズ 0〜4 の PR がすべてマージされている。
- 今日の画面を開いて 3 秒以内に「次にやる 1 件」が分かり、1 タップで完了でき、完了すると報酬の演出が出る。
- 全画面がライト / ダーク、PC / スマホで崩れず、キーボードだけで主要な操作ができる。
- pytest・`npm run build`・`npm run test:device` がすべて通る。2 ユーザーの分離テストも通る。
- `docs/redesign/GAME_UI_DIRECTION.md`（採用したデザインと理由）と、必要なら `docs/redesign/ASSETS.md`（素材の出典）が残っている。
